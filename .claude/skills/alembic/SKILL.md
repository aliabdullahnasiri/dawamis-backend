# Alembic Migration

## Purpose

Use this skill only for:

1. Creating Alembic migrations from SQLAlchemy model changes.
2. Applying migrations to the database.

This project uses `uv`, so all Alembic commands MUST be executed with `uv run`.

---

## 1. Check Current Migration State

Before creating a migration, run:

```bash
uv run alembic current
uv run alembic heads
```

Check that the database and migration history are in a valid state.

---

## 2. Create a Migration

When SQLAlchemy models have changed, create an autogenerated migration:

```bash
uv run alembic revision --autogenerate -m "<description>"
```

Use a short, descriptive migration message.

Examples:

```bash
uv run alembic revision --autogenerate -m "add email verification fields"
```

```bash
uv run alembic revision --autogenerate -m "create attendance table"
```

```bash
uv run alembic revision --autogenerate -m "add medicine stock indexes"
```

---

## 3. Review the Generated Migration

After generating the migration, inspect the generated file.

Use:

```bash
git diff
```

or inspect the newest file in:

```text
alembic/versions/
```

Do NOT blindly trust Alembic autogeneration.

Check that:

* The intended model changes are included.
* No unrelated changes were generated.
* Foreign keys are correct.
* Indexes are correct.
* Constraints are correct.
* Nullable changes are correct.
* Existing data will not be unintentionally destroyed.

### Important: Renames

If a column was renamed, make sure Alembic did not generate:

```text
drop old column
add new column
```

A real rename should preserve the existing data.

Do not accept destructive autogenerated operations without reviewing them.

---

## 4. Apply the Migration

After reviewing the migration:

```bash
uv run alembic upgrade head
```

Then verify:

```bash
uv run alembic current
```

The database should now be at the latest migration.

---

## 5. Migration Description

Use concise descriptions.

Good:

```text
add email verification fields
create employee attendance table
add medicine stock indexes
add user organization relationship
```

Avoid:

```text
update database
changes
migration
fix
new changes
```

---

## 6. One Logical Change

Create a migration based on the logical database change.

Multiple model changes that belong to the same feature can be included in one migration.

For example:

```text
User model
    ├── email_verified
    ├── email_verification_token
    └── email_verification_expires_at
```

can be one migration:

```text
add email verification fields
```

Do not create one migration per changed file.

---

## 7. Safety Rules

* Always use `uv run alembic`.
* Always review autogenerated migrations before upgrading.
* Never run destructive database operations automatically.
* Never delete existing migration files.
* Never modify an already-applied migration to fix a new schema change.
* Never use `git reset --hard`.
* Never run migrations against production unless explicitly requested.
* Never commit secrets or database credentials.
* Do not run downgrade commands as part of this skill.
* Do not use `--sql` as a replacement for reviewing the migration.

---

## Standard Workflow

For a normal SQLAlchemy model change:

```bash
uv run alembic current
uv run alembic heads

uv run alembic revision --autogenerate -m "<description>"

git diff

uv run alembic upgrade head

uv run alembic current
```

The expected workflow is:

```text
SQLAlchemy model changes
        ↓
Check migration state
        ↓
Generate migration
        ↓
Review migration
        ↓
Upgrade database
        ↓
Verify current revision
```
